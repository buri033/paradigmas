1. ARQUITECTURA GENERAL
════════════════════════════════════════════════════════════════════════════════

DuckBank usa una arquitectura **monolítica Django** con 7 apps independientes:

    duckbank/          ← Configuración del proyecto (settings.py, urls.py)
    ├── users/          ← Gestión de usuarios y autenticación
    ├── accounts/       ← Cuentas digitales
    ├── transactions/   ← Transferencias, depósitos, retiros
    ├── savings/        ← Cajitas de ahorro (interés compuesto)
    ├── loans/          ← Créditos, tarjetas, simulador
    ├── notifications/  ← Notificaciones
    └── money_requests/ ← Solicitudes de dinero P2P

Cada app sigue el patrón MTV (Model-Template-View) de Django, pero como
usamos DRF (Django REST Framework), la estructura real es:

    models.py      → Definición de tablas de la base de datos
    serializers.py → Conversión entre modelos y JSON (entrada/salida de la API)
    views.py       → Lógica de negocio (endpoints)
    urls.py        → Rutas URL que conectan con las vistas
    signals.py     → Acciones automáticas (triggers) cuando ocurren eventos

El frontend (carpeta paradigmas/) consume la API REST enviando peticiones
HTTP con JWT (JSON Web Tokens) para autenticación.

2. AUTENTICACIÓN — CÓMO FUNCIONA JWT
════════════════════════════════════════════════════════════════════════════════

JWT (JSON Web Token) es un estándar de autenticación sin estado (stateless).
Funciona así:

1. El usuario envía email + contraseña a POST /api/auth/login/
2. El servidor valida las credenciales y devuelve DOS tokens:
   - **access token**: válido por 60 minutos, se envía en cada petición
   - **refresh token**: válido por 1 día, se usa para obtener un nuevo access

3. En cada petición a la API, el frontend envía el header:
       Authorization: Bearer <access_token>

4. Cuando el access token expira, el frontend usa el refresh token para
   obtener uno nuevo en POST /api/auth/refresh/

5. Al hacer logout, el refresh token se agrega a una blacklist (lista negra)
   para que no pueda ser reutilizado.

Configuración en settings.py:
    SIMPLE_JWT = {
        'ACCESS_TOKEN_LIFETIME': timedelta(minutes=60),
        'REFRESH_TOKEN_LIFETIME': timedelta(days=1),
        'ROTATE_REFRESH_TOKENS': True,        # Genera nuevo refresh cada vez
        'BLACKLIST_AFTER_ROTATION': True,      # Invalida el refresh anterior
    }

ARCHIVOS CLAVE:
- users/views.py → RegisterView, LogoutView
- users/serializers.py → RegisterSerializer
- paradigmas/js/api.js → AuthAPI (login, register, logout, getProfile)

SEÑAL CRUCIAL (transactions/signals.py):
CADA VEZ que se crea una Transaction, se actualiza automáticamente
el saldo de la cuenta:

    @receiver(post_save, sender=Transaction)
    def update_account_balance(sender, instance, created, **kwargs):
        if created:
            account = instance.account
            if instance.type == 'income':
                account.balance += instance.amount      # Suma al saldo
            elif instance.type in ('expense', 'transfer'):
                account.balance -= instance.amount      # Resta del saldo
            account.save()

Esto significa que NUNCA se modifica el saldo directamente — siempre
se crea una Transaction y el signal se encarga de actualizar el saldo.

TRANSFERENCIAS ATÓMICAS (transactions/views.py → TransferView):
Las transferencias usan @db_transaction.atomic (decorador de Django).
Esto garantiza que si algo falla a mitad de la operación, se revierte TODO
(rollback). Si se descuenta del remitente pero falla el depósito al
destinatario, nada se guarda en la base de datos.

PREGUNTA DE SUSTENTACIÓN: ¿Por qué usar transacciones atómicas?
RESPUESTA: Para garantizar la integridad de los datos. Si la transferencia
falla a mitad (ej: error de red), el dinero no se pierde — todo se revierte.

CÁLCULO DEL INTERÉS COMPUESTO:

El interés se calcula diariamente con capitalización compuesta:

    Fórmula diaria:  interés_diario = balance × (1 + rate/36500) - balance
                     nuevo_balance = balance × (1 + rate/36500)

    Que es equivalente a:  balance × (1 + tasa_anual/36500)

Ejemplo con 11% anual:
    - Tasa diaria = 11% / 365 = 0.03014%
    - Factor diario = 1 + 0.11/365 = 1.0003014
    - Si tienes $100,000 en la cajita:
      Día 1: $100,000 × 1.0003014 = $100,030
      Día 2: $100,030 × 1.0003014 = $100,060
      ... al cabo de 365 días: $100,000 × (1.0003014)^365 ≈ $111,000

SERIALIZER (savings/serializers.py):
SavingsBoxSerializer calcula la ganancia proyectada anual:
    projected_annual_earnings = balance × ((1 + rate/365)^365 - 1)

COMANDO CRON (savings/management/commands/calculate_interest.py):
Se ejecuta diariamente a medianoche:
    python manage.py calculate_interest

Recorre todas las cajitas activas, calcula el interés diario y lo suma
al balance. También guarda un registro en SavingsBoxInterestLog.

PREGUNTA DE SUSTENTACIÓN: ¿Qué es el interés compuesto?
RESPUESTA: Es cuando los intereses generados se suman al capital, y los
nuevos intereses se calculan sobre el capital + intereses anteriores.
En DuckBank se capitaliza diariamente: cada día se suma un pequeño interés
al saldo, y al día siguiente el interés se calcula sobre ese nuevo saldo.

SIMULADOR DE CRÉDITO — Amortización Francesa (loans/views.py → SimulateLoanView):

La amortización francesa es el sistema más común en préstamos bancarios.
La cuota mensual es FIJA durante todo el préstamo.

    Fórmula:  M = P × r × (1+r)^n / ((1+r)^n - 1)

    Donde:
        M = cuota mensual fija
        P = monto del préstamo (principal)
        r = tasa de interés mensual (ej: 1.15% = 0.0115)
        n = número de cuotas (plazo en meses)

Ejemplo:
    Préstamo de $5,000,000 a 24 meses con tasa 1.15% mensual:
    M = 5,000,000 × 0.0115 × (1.0115)^24 / ((1.0115)^24 - 1)
    M ≈ $235,335

Características de la amortización francesa:
- La cuota es CONSTANTE (siempre la misma)
- Los intereses son mayores al inicio y disminuyen con el tiempo
- El abono a capital es menor al inicio y aumenta con el tiempo
- Es el sistema más usado en Colombia y Latinoamérica

VISTAS:
- PayLoanQuotaView: Descuenta cuota de la cuenta, actualiza paid_quotas
  y remaining. Si paid_quotas >= total_quotas, cambia status a 'paid'.
- ToggleCardLockView: Alterna entre 'active' y 'locked'
- PayCardView: Paga deuda de tarjeta desde una cuenta, descuenta de used_amount

FLUJO DE SOLICITUD DE DINERO:

1. CREAR (CreateMoneyRequestView):
   - El solicitante envía email del destino + monto + descripción
   - Se busca el usuario destino por email
   - Se crea MoneyRequest con status='pending'
   - Se envía notificación al destino

2. ACEPTAR (AcceptMoneyRequestView):
   - El destino verifica que tiene saldo suficiente
   - Se ejecuta dentro de db_transaction.atomic():
     a. Se crea transacción de gasto en la cuenta del destino
     b. Se crea transacción de ingreso en la cuenta del solicitante
     c. Se cambia status a 'accepted'
   - Se envía notificación de éxito al solicitante
   - Si algo falla, todo se revierte (atomicidad)

3. RECHAZAR (RejectMoneyRequestView):
   - Se cambia status a 'rejected'
   - Se envía notificación de rechazo al solicitante
   - No se mueve dinero

RELACIONES CLAVE:
- User ←→ Profile: OneToOneField (1:1) — Cada usuario tiene exactamente un perfil
- Profile ←→ Account: ForeignKey (1:N) — Un perfil puede tener varias cuentas
- Profile ←→ Transaction: ForeignKey (1:N) — Un perfil tiene muchas transacciones
- Account ←→ Transaction: ForeignKey (1:N) — Una cuenta tiene muchas transacciones
- Profile ←→ SavingsBox: ForeignKey (1:N) — Un perfil puede tener varias cajitas
- SavingsBox ←→ InterestLog: ForeignKey (1:N) — Una cajita tiene muchos registros
- Profile ←→ Loan: ForeignKey (1:N) — Un perfil puede tener varios créditos
- Profile ←→ Card: ForeignKey (1:N) — Un perfil puede tener varias tarjetas
- Profile ←→ Notification: ForeignKey (1:N) — Un perfil tiene muchas notificaciones
- Profile ←→ Contact: ForeignKey (1:N) — Un perfil tiene muchos contactos
- Profile ←→ MoneyRequest: ForeignKey (1:N) como requester Y como target

NOTA SOBRE UUIDs: Todos los modelos principales usan UUIDField como primary key
en vez de AutoField. Esto tiene ventajas:
1. Seguridad: No se puede adivinar el ID de otro registro
2. Escalabilidad: Se puede generar el ID del lado del cliente
3. Migración: Facilita la fusión de datos de diferentes instancias

11. DJANGO SIGNALS — ACCIONES AUTOMÁTICAS
════════════════════════════════════════════════════════════════════════════════

Los signals son como "triggers" de base de datos pero a nivel de Django.
Se ejecutan automáticamente cuando ocurre un evento en un modelo.

SIGNAL 1: Crear perfil automáticamente (users/signals.py)
    CUÁNDO: Después de crear un User (post_save)
    QUÉ HACE: Crea un Profile vacío asociado al nuevo User
    POR QUÉ: Para que siempre exista un perfil, sin necesidad de crearlo manualmente

SIGNAL 2: Crear cuenta por defecto (accounts/signals.py)
    CUÁNDO: Después de crear un Profile (post_save)
    QUÉ HACE: Crea una "Cuenta Vista" con saldo inicial de $4,850,900 COP
    POR QUÉ: Todo usuario nuevo necesita al menos una cuenta bancaria

SIGNAL 3: Actualizar saldo (transactions/signals.py)
    CUÁNDO: Después de crear una Transaction (post_save, solo si created=True)
    QUÉ HACE:
        - Si type == 'income' → suma el monto al balance de la cuenta
        - Si type == 'expense' o 'transfer' → resta el monto
    POR QUÉ: Para mantener el saldo sincronizado con las transacciones.
    NUNCA se modifica el saldo directamente — siempre se crea una transacción
    y el signal actualiza el saldo automáticamente.

12. SERIALIZERS — CÓMO SE CONVIERTEN LOS DATOS A JSON
════════════════════════════════════════════════════════════════════════════════

Los serializers son la capa que transforma los modelos de Django (objetos Python)
a JSON (para la API) y viceversa. Son como "traductores" entre la base de datos
y el frontend.

TIPOS DE SERIALIZERS USADOS:

1. ModelSerializer: Mapea directamente un modelo a JSON
   Ejemplo: TransactionSerializer, NotificationSerializer, LoanSerializer
   - Define fields = [...] para elegir qué campos incluir
   - Define read_only_fields = [...] para campos que no se pueden modificar

2. Serializer (sin modelo): Para validación de entrada
   Ejemplo: TransferSerializer, DepositSerializer, WithdrawalSerializer
   - Solo validan los datos de entrada (amount, account_id, etc.)
   - No guardan directamente en la base de datos
   - La vista se encarga de crear los objetos usando los datos validados

3. SerializerMethodField: Para campos calculados
   Ejemplo: AccountSerializer.display_balance
   - Llama a get_display_balance() que retorna '***' o el saldo real
   Ejemplo: SavingsBoxSerializer.projected_annual_earnings
   - Calcula la ganancia proyectada anual con interés compuesto

FLUJO TÍPICO DE UNA PETICIÓN:

1. El usuario hace clic en un botón (ej: "Transferir")
2. El JS llama a TransfersAPI.transfer({ account_id, amount, ... })
3. apiFetch() agrega el header Authorization: Bearer <token>
4. Se envía POST /api/transfers/ al backend
5. Django verifica el JWT, ejecuta la vista
6. La vista valida datos con el serializer
7. Si es transferencia, usa @db_transaction.atomic
8. Se crea la Transaction, el signal actualiza el saldo
9. Se retorna JSON con el resultado
10. El JS actualiza la interfaz con la respuesta

Intl.NumberFormat('es-CO') para mostrar montos como "$4.850.900".

14. CORS — POR QUÉ FUNCIONA DESDE EL FRONTEND
════════════════════════════════════════════════════════════════════════════════

CORS (Cross-Origin Resource Sharing) es un mecanismo de seguridad del
navegador que bloquea peticiones entre orígenes diferentes (distinto
protocolo, dominio o puerto).

El frontend corre en file:// o localhost:5500 y el backend en localhost:8000.
Sin CORS configurado, el navegador bloquearía las peticiones.

En settings.py:
    CORS_ALLOWED_ORIGINS = [
        'http://localhost:5500',
        'http://127.0.0.1:5500',
        'http://localhost:8000',
        ...
    ]
    CORS_ALLOW_ALL_ORIGINS = True   # Para desarrollo local

En producción, CORS_ALLOW_ALL_ORIGINS debe ser False y solo se permiten
los orígenes confiables.

16. PREGUNTAS FRECUENTES DE SUSTENTACIÓN
════════════════════════════════════════════════════════════════════════════════

P: ¿Qué patrón de arquitectura usa el proyecto?
R: Arquitectura monolítica con Django REST Framework. El frontend (HTML/CSS/JS)
   consume la API REST del backend. No hay separación en microservicios.

P: ¿Por qué UUID en vez de IDs auto-incrementales?
R: Por seguridad (no se pueden adivinar otros IDs), escalabilidad (se pueden
   generar del lado del cliente) y para facilitar migración de datos.

P: ¿Cómo se asegura la integridad en las transferencias?
R: Con transacciones atómicas de base de datos (@db_transaction.atomic).
   Si cualquier paso falla, todo se revierte (rollback).

P: ¿Cómo funciona el interés compuesto de las cajitas?
R: Cada día se calcula: balance × (1 + tasa_anual/36500). El interés diario
   se suma al saldo, y al día siguiente se calcula sobre el nuevo saldo.
   Esto genera un efecto "bola de nieve": el interés genera interés.

P: ¿Qué es la amortización francesa?
R: Un sistema de préstamos donde la cuota mensual es FIJA. Al inicio se paga
   más interés y menos capital; al final se paga menos interés y más capital.
   La fórmula es: M = P × r × (1+r)^n / ((1+r)^n - 1).

P: ¿Qué son los signals en Django?
R: Son callbacks que se ejecutan automáticamente cuando ocurre un evento en
   un modelo (post_save, pre_delete, etc.). En DuckBank se usan para:
   - Crear Profile al crear User
   - Crear Cuenta Vista al crear Profile
   - Actualizar saldo al crear Transaction

P: ¿Cómo se autentica al usuario?
R: Con JWT (JSON Web Tokens). El cliente envía email+contraseña, recibe un
   access token (60 min) y un refresh token (1 día). El access token se
   envía en el header Authorization: Bearer <token> en cada petición.

P: ¿Qué es un serializer en DRF?
R: Es una clase que convierte datos complejos (modelos de Django) a JSON
   y viceversa. También valida los datos de entrada. Es como un "traductor"
   entre la base de datos y la API REST.

P: ¿Por qué se usa BigIntegerField para los montos?
R: Porque el Peso Colombiano (COP) no usa decimales. Un BigIntegerField
   permite almacenar montos hasta 9.2 × 10^18, suficiente para cualquier
   operación bancaria real sin necesidad de manejar decimales.

P: ¿Qué hace el archivo api.js en el frontend?
R: Es el cliente HTTP que centraliza todas las llamadas a la API. Maneja:
   - Tokens JWT (guardar, renovar, eliminar)
   - Headers de autorización automáticos
   - Manejo de errores (401 = token expirado)
   - Métodos para cada endpoint (login, transferir, crear cajita, etc.)

P: ¿Qué es CORS y por qué es necesario?
R: CORS (Cross-Origin Resource Sharing) es una política de seguridad del
   navegador que bloquea peticiones entre dominios diferentes. Como el
   frontend y backend corren en puertos distintos, necesitamos configurar
   CORS en Django para permitir las peticiones del frontend.
